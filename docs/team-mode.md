# 工作区团队模式

团队模式把同一工作区的独立 Codex 会话组成关系图。会话保留原 ID、历史、模型设置和单独对话入口；团队提供通信关系、审批与投递，不会把这些会话改成临时子智能体。

每个工作区单独开启，默认关闭，也不会自动把已有会话加入团队。此前的隔离验证仍可通过[团队试验](team-pilot.md)使用。

## 开启与加入已有会话

1. 在左侧**工作区名称**上右键，勾选「团队模式」。菜单针对右键的工作区，即使当前正在查看另一个工作区的会话。
2. 选择「打开关系图」，或使用顶部「对话／团队」切换。
3. 在关系图中选择「加入会话」，先选唯一的第一层负责人，再选择第二层主管和后续执行成员。为每位成员设置直属上级与分组；候选列表只包含当前工作区的会话。
4. 检查箭头方向和审批策略。拖动连线可调整单向、双向或不通信；双击节点可返回该成员的原会话。
5. 在右侧「审批」页查看请求。默认采用手动审批，必须获得你确认才能投递。可勾选多项独立任务后一次批准，或打开单条申请修改正文与填写备注。

加入已有会话不创建副本，不删除或合并旧记录，不发送“初始化任务”，也不消耗模型用量。正在执行的会话仍可加入关系图；它的当前轮次不会被停止或插话。团队工具在可安全接入时启用，排队任务在接收方空闲且工具就绪后投递。

新增会话与加入已有会话是两个入口。新增申请始终需要用户批准；申请中可使用设置里的默认模型、推理强度，或单独指定。模型实际支持的档位由原生 Codex 返回，不能用不受支持的档位创建。

加入或申请成员成功后，浏览器会按工作区记住层级，并分别记住每层的直属上级、每个上级下的分组。下次打开表单或切回该层时自动恢复有效选择；从节点右键加入下级时，以点选的上级为准。取消或失败不会覆盖上次成功的选择，已失效的层级和分组会重新校验。

### 移出团队

在关系图的**会话节点上右键 → 移出团队**，核对影响后确认。原生会话、历史与正在执行的轮次会保留，仍可单独对话，之后也可从「加入会话」重新加入。

有直属下级的成员需要选择一位同层级的接替上级；下级层级、分组和原有上下级通信方向保留。若没有可接替的同层成员，先调整下级归属或加入接替成员。最高负责人仍有下级时不能直接移出。

移出会取消该会话尚未投递的通信，关闭相关待批准成员申请，保留这些记录。其他受上级或审核关系变化影响的通信重新等待用户审批，无关队列保持原有授权。投递／创建正在提交，或相关结果仍待核对时，会提示稍后再操作。成员移出与重新加入均不调用模型。

前端热更新后若提示服务尚未支持该操作，需在会话空闲后正常运行 `cweb restart --no-browser`，再刷新网页。正在执行任务时不要强制重启。

## 会话较多时查看关系图

层级从左到右排列，同层成员从上到下排列；同一直属上级的成员与分组保持相邻，父节点对齐其子树的中部。没有成员的层级不占画布空间。排版只改变显示，不调整层级、分组归属或通信权限。

- 默认「清晰视图」保留可读大小，可拖动画布查看其余成员。
- 「定位分组」可直接查看某组及其上级；「全图」用于观察整个团队的结构。
- 节点标题过长时可悬停查看完整名称，双击进入原会话。
- 同组成员可上下拖动排序；状态刷新保留当前缩放与查看位置。
- 上下级用平滑曲线连接，端点对齐时直接连接；同层相邻节点优先使用最近端点，存在遮挡时才用外弧绕过节点。

右侧工作区面板可拖动左边缘调整宽度，也可聚焦边缘后按左右方向键调整；双击边缘恢复默认。宽度在本机保存，屏幕变窄时自动限制，不挤掉对话区域。手机仍使用适合屏幕的侧栏宽度。

## 关系与审批

| 规则 | 行为 |
| --- | --- |
| 第一层 | 只有一位最高负责人 |
| 后续层级 | 每位成员只有一个直属上级，分组归属不交叉；默认三层，可增加 |
| 上下级通信 | 只能在直接相邻的直属层级之间通信，并遵守箭头方向 |
| 同层、同一上级 | 默认沿已开放的箭头直接沟通，旧模式由共同上级审核一次 |
| 同层、不同分组 | 默认可沿已开放的箭头跨组协商，旧模式由双方直属上级分别审核 |
| 越级或跨工作区 | 不投递；跨组协作可通过允许的同层关系或各自上级转达 |
| 暂停团队模式 | 保留关系和历史，停止新投递；已经开始的轮次仍在原会话中管理 |

在**设置 → 团队协作 → 同级协作方式**选择「直接协商，按需上报」或「先由直属上级审核」。新旧工作区默认直接协商；切换只影响之后提出的通信，已排队或待审的事项沿用提出时的方式。

遇到分歧时，约定一方把问题、双方选项和建议发给自己的直属上级（用问题关联收到的同级消息）。获得决定后，由提问的一方沿开放的连线同步给对方。建议为需要来回协商的成员设置双向连线。

在**设置 → 团队协作 → 通信审批**选择当前工作区的审批策略。审批侧栏的设置按钮和网页命令 `/team` 都能直达这一页。暂停团队后也可以先配置规则，再开启投递。

- **手动审批**：任务、问题、反馈由你确认。
- **自动审批**：图中的有效路线由固定规则批准。同级直连可直接投递，旧模式仍需上级审核。
- **AI 自主判断风险**：由发送方的直属上级在只读轮次内判断风险。最高负责人没有上级，申请直接显示在网页上，由用户确认。

只有当前工作区开启团队模式时，右侧栏才显示「审批」标签。切换到普通工作区会回到待办（未启用待办时回到变更）；关闭团队模式会保留原有待审批记录。

审批正文与新成员职责说明支持 Markdown 标题、列表、强调、表格和代码块，并沿用文件预览与链接交互。编辑时保留原始 Markdown，投递内容不会因排版改变；正文中的交互组件代码只作为文本审阅。

团队消息会标明通信审批方式与是否经用户确认。批准的是消息投递，不会扩大接收会话的权限，也不替代命令、文件或设备操作所需的授权。编写任务时应说明项目范围、目标、已有证据和交付要求，保留技术事实与限制。

如果模型返回明确的内容安全拦截，网页会显示「模型内容安全拦截」及原始错误，而不是把它当作断网。此类失败不自动重发或改写；需要结合本轮已执行的步骤核对，不能只凭错误提示确定是哪条消息或工具输出触发。清楚的任务说明有助于理解，但不能保证上游模型不会拒绝请求。

收到明确的转发任务时，会话可直接提出新的通信申请。需要人工决定时，在对话输入框上方点「查看并审批」即可核对收发双方和正文。在审批侧栏的「全部记录」中，也可打开已送达消息，点「转发给其他成员」，选好收件人并核对正文后确认。手动转发由桥接程序登记，无需发件会话再次运行。

查看关系、拖动排列、路由判断、普通手动／自动审批与排队调度不调用模型。上级审核、AI 风险判断和实际处理任务会调用模型。审批策略改变后，已有请求保留原流程；修改通信权限或成员归属会使尚未投递的旧授权失效，需要重新审核。

## 多任务如何并行

**不同接收会话可以同时处理各自的任务，同一接收会话按队列顺序处理。**

在**设置 → 团队协作 → 任务分工偏好**选择「按负载权衡」「优先自己完成」或「优先并行分工」。会话在当前轮做决定。小修正可直接做完；需要专长、自己已有积压时可委派；主线与测试可独立推进时，也可保留主线，把测试交给下级。

权衡分工时，团队成员工具可以返回本人和允许派工的直属成员的负载快照，包括已观察到的运行状态、用户排队数、待投递通信和待审核数量。缺少观测的会话标为未知。预计收益还取决于任务依赖、共享文件、交付往返和整合工作，快照只供当轮参考。

负责人或主管可在一轮内提交多项独立工作，无需等待上一项回复。打开右侧「审批」，勾选可以同时开工的任务，再点「批准所选任务」。每项仍保留单独的审批记录，必要的上级或风险审核仍按原规则执行。若提交时有任一所选任务的版本已变化，整次批准会停止，请核对更新后的内容再选择。

等待同一位审核人的请求可共用一次审核轮次，每项分别得到判断。某项审核通过后即可进入对应接收会话的队列，其他项目的审核继续进行。

简单任务可由当前会话直接完成。收到结果后即可收尾；如需对方修正，发起关联该结果的新任务或具体问题。主管可把多份交付整理为一次阶段结论，并关联上级的原任务。

会话空闲时，队首有 3 条或更多已批准通信，或恰有 2 条已批准的结果反馈时，会自动合并为一条消息。单条结果就绪时直接投递。也可以展开「团队队列」，在至少有 2 条可合并的通信时点「合并投递」。每批最多 8 条，标题与正文合计最多约 3 万字符，装不下的条目继续排队。批次在提交时固定，新入队的条目留到下一轮。程序按登记顺序拼接原文，保留每条通信的发件人、审批记录和消息 ID。

待审批的请求等到获准后才能投递。排在中间的审核请求会分隔通信批次，审核在专用轮次完成。批次回执不明时，可通过其中任一条通信核对整批回执。

对话页输入框上方会显示本会话的「团队队列」。展开可查看来源、标题、状态与排队顺序，点击「查看审批」会在右栏定位该条请求，当前聊天和草稿保留。未获批准的请求仍会显示，但不会执行；需要核对的回执会明确标注。通过 Tab 排队的用户消息优先于团队任务。队列条目移出仅代表已投递，任务执行结果仍以会话输出及后续反馈为准。

每个团队最多同时进行 4 个不同接收方的可用性检查与投递，避免一个缓慢请求挡住整个队列。模型接收后即可释放投递名额，因此这不是“最多运行 4 个模型”；各成员仍按原生运行状态和账户额度执行。

调度遵守以下条件：

- 接收方正在执行、压缩上下文、等待用户回答或已有用户排队消息时，团队任务等待，不自动插话。
- 由其他终端持有的活动会话保留原端控制；cweb 不终止终端或抢走当前轮次。
- 上级审核也是该上级会话中的独立轮次。同一个上级不会因为多条申请而同时收到多个冲突的轮次。
- 投递结果未知时，暂停向该接收方继续投递，保留「需核对」与回执入口；其他可用接收方仍能继续。无法确认原生接收凭据时不自动重发。

并行单位是会话，不是文件锁。多个成员共享同一工作区文件，分工时应明确各自负责的文件或模块；关系图不会隔离并发修改。

## 为什么刷新后还看不到入口

前端文件与后台桥接服务是两部分。只刷新网页不能让旧后台加载新功能。

- 新版前端会检测后台能力。后台尚未启用团队能力时，入口会说明需要更新服务；这时不能把图上的设置当成已生效。
- 开发维护时可先热更新前端，保留旧版静态资源供已打开的页面使用；此步骤不重启桥接或打断原生轮次。
- 后端更新必须等 cweb 自有任务全部空闲。维护者先用 `cweb status` 确认，再执行普通的 `cweb restart --no-browser`；自定义端口时加上 `--port 原端口`，并保持原来的数据目录环境设置。该命令在仍有任务时拒绝停止；不要为了显示入口使用 `--force`。
- 后台更新后刷新网页，再右键工作区名称开启。旧的隔离试验地址与日常网页有独立数据，试验图不会自动成为真实工作区关系图。

正式服务的 `/api/bootstrap` 返回 `capabilities.teamMode: true`；`teamPilot: true` 仅表示隔离试验。`GET /api/teams` 列出工作区团队摘要；管理请求通过 `?workspace=<工作区 ID>` 明确作用范围。原生工具使用绑定会话的本地凭据，不能靠修改请求中的工作区或发件人冒充其他成员。

## 原生会话与部署边界

原生 Codex 继续保存会话历史。cweb 通过会话所属的原生引擎发送、读取和处理批准，不复制数据库或直接改写历史文件。旧会话无法通过恢复操作更换已有动态工具列表，因此使用会话范围的 `cweb_team_*` MCP 接入；名称同时绑定数据目录和本机服务地址，避免误用其他安装或旧端口的工具。只有空闲、没有其他端占用且成功检查工具状态后才使用。该接入不会覆盖用户的全局 Codex 配置。

团队功能不会改变已导入会话的模型和文件权限。普通任务沿用该会话设置；审核轮次的用途是判断待审请求，不执行待审正文。通信审批约束 cweb 通道，不能替代同一系统账户下文件权限或进程隔离。

对于此前只在 CLI 中使用、尚无网页设置的会话，首次空闲接入会读取原生恢复结果，再保存其模型、推理强度和权限。遇到尚不支持的原生权限配置，自动投递会要求在会话设置中明确选择，而不是使用全局默认权限替代。

默认保留每团队最多 80 名成员、1,000 条通信及 200 条成员申请。工作区状态独立保存于本机私有数据目录；多实例同时写同一份数据及长期审计归档仍需单独设计。迁移时应连同 cweb 私有数据一起备份，方法见[私人迁移包](migration-package.md)。

## 开发验证

工作区作用域、旧会话导入、权限和原生协议的模拟回归不调用真实模型：

```bash
cd bridge
node --test tests/workspace-teams.test.ts tests/team-integration.test.ts
```

模拟通过不代表实际模型已执行；涉及模型的完整验收优先在隔离试验工作区进行，不向用户实际工作区自动派发测试任务。

## 在一个会话里只看自己的对话

默认只显示你的提问和相应回复。点会话顶栏的「显示团队」，可以按时间顺序一起阅读团队任务、反馈和审核；点「隐藏团队」即可回到个人对话。如果隐藏后对话区还有空位，网页会逐页补载更早的消息，每次最多 8 页。继续上滚或点击「显示更早的消息」可再往前读。

**设置 → 团队协作 → 显示团队消息** 与顶栏共用一个开关。选择按工作区保存在当前浏览器，切换会话和刷新页面后仍然生效。

筛选只影响网页阅读。原生会话保留完整上下文，团队任务照常投递。旧记录如果无法和团队投递记录核对，会继续显示在普通对话中。

## 团队任务的完工通知

由接下整体任务的会话核对交付和验收结果。全部条件达成后，它通过 `team_report_completion` 发送一次通知，写明交付了什么、怎样验证。子任务的反馈沿原团队路线汇总。需要你亲自验收的工作，仍须等你确认。

通知出现在网页右下角，可以从其他会话跳回负责会话。开启「隐藏团队」后仍能看到；已读的通知保存在负责会话底部的「团队完工通知」里。

使用 Ubuntu 桌面浏览器时，可在「设置 → 常规」开启「会话完成桌面通知」，并在浏览器提示时选择允许。保留一个 cweb 标签页，即使切到其他应用，也能在任一会话每轮处理完成时收到系统横幅。点击横幅可返回对应会话。团队整体完工时会单独显示任务标题和负责会话。关闭所有 cweb 标签页后，未读记录会在下次打开网页时显示。
